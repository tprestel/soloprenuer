Executive Summary

The migration from Squarespace to HubSpot is a massive improvement across every measurable SEO dimension. The old site had zero H1 tags sitewide, no meaningful schema, and actively blocked AI crawlers. The new site has proper heading hierarchy on every page, rich JSON-LD on all 19 pages, full coverage of all 6 locations, and clean URL structure.

However, several issues introduced by the migration need to be resolved before the site reaches its ranking potential. The most critical are: robots.txt returns a 404 (Google cannot read crawl rules and has no sitemap pointer), meta descriptions are missing on 15 of 19 pages, canonical URLs use the non-www version while the live domain serves www, internal links are polluted with ?hsLang=en parameters, and multiple pages have runaway H1 usage (some pages have 8–10 H1 tags instead of one).

The schema implementation is genuinely strong — each location page has a full LaundryOrDryCleaning schema with address, coordinates, hours, and ratings; service pages have Service and FAQPage schemas; the careers page has a JobPosting schema. This is a real competitive advantage. It just needs the technical scaffolding around it to be clean.

Fix the 6 critical issues first. With those resolved, this site is in strong shape to begin ranking for local intent keywords within 60–90 days.

01

Technical Findings

High
robots.txt returns 404 — Google has no crawl rules or sitemap pointer
Fetch of /robots.txt returned HTTP 404. Google and all other crawlers receive an error instead of crawl directives.
▾

A missing robots.txt is not a catastrophic crawling failure — Google will crawl everything when no robots.txt exists — but it does mean:

  • No Sitemap: directive to surface the XML sitemap to crawlers
  • No ability to block internal HubSpot utility paths or thank-you pages from the index
  • AI crawlers (GPTBot, ClaudeBot, anthropic-ai, Google-Extended) have no explicit allow signal — their default behavior varies by bot
  • The Semrush, Ahrefs, and Majestic crawlers also check robots.txt for crawl budget management

On the old Squarespace site, robots.txt actively blocked AI crawlers. While the HubSpot site does not inherit those blocks, it's best practice to explicitly allow valuable AI bots.

Fix

In HubSpot, go to Settings → Website → Pages → SEO → Custom robots.txt. Add the following:

  • User-agent: * then Allow: /
  • Explicit allow for GPTBot, ClaudeBot, anthropic-ai, Google-Extended
  • Disallow any HubSpot form thank-you variants, e.g. /hs-landing-pages/ if applicable
  • Add: Sitemap: https://www.superlaundry24.com/sitemap.xml
High
Canonical tags point to non-www; live domain serves www
All canonical tags use https://superlaundry24.com/ but the site serves on https://www.superlaundry24.com/. This creates a URL inconsistency that can split link equity.
▾

The canonical URL on every page sampled uses the non-www version:

  • Homepage canonical: https://superlaundry24.com/
  • Avondale canonical: https://superlaundry24.com/locations/avondale
  • Westwood canonical: https://superlaundry24.com/locations/westwood
  • North College Hill canonical: https://superlaundry24.com/locations/north-college-hill
  • Wash & Fold canonical: https://superlaundry24.com/services/wash-and-fold
  • Pickup/Delivery canonical: https://superlaundry24.com/services/pickup-delivery
  • Self-Service canonical: https://superlaundry24.com/services/self-service
  • 24-Hour canonical: https://superlaundry24.com/services/24-hour-laundry

The browser resolves to https://www.superlaundry24.com/. If Google follows the canonical and indexes the non-www version, then any direct links to www URLs will not consolidate properly. It also creates inconsistency with external links, GBP listings, and schema url values.

Fix

In HubSpot, go to Settings → Website → Domains & URLs and confirm whether non-www redirects to www. Then in the page settings for each page template, update the canonical domain to match: either commit to www.superlaundry24.com across all pages and all schema url fields, or commit to non-www and make sure that version is the one that resolves. Pick one. Consistency is what matters — the JSON-LD schema url values must also match whichever version you choose.

High
Internal links include ?hsLang=en parameter — HubSpot multi-language artifact
34 of 44 links on the Avondale page (sample) include ?hsLang=en. These are technically different URLs from the canonical and may cause indexation confusion.
▾

HubSpot's multi-language system appends ?hsLang=en to internal navigation links when a site is configured with language variations. Since superlaundry24.com is English-only, these parameters serve no purpose and create noise. Every page in the navigation and footer generates URLs like:

  • https://www.superlaundry24.com/?hsLang=en
  • https://www.superlaundry24.com/services?hsLang=en
  • https://www.superlaundry24.com/locations?hsLang=en

Google's crawler will typically canonicalize these to the non-parameter version, but it adds unnecessary URL variants, wastes crawl budget, and can create duplicate content signals. HubSpot may also generate separate page variants with these URLs in its internal crawl logic.

Fix

In HubSpot, go to Settings → Website → Pages → Language & Region. If multi-language is enabled and the site is English-only, turn off the multi-language feature entirely. This will stop the ?hsLang=en parameter from being appended to internal links. If multi-language cannot be disabled, add a URL parameter rule in Google Search Console under Legacy Tools → URL Parameters indicating that hsLang does not change page content.

Multiple H1 tags on most pages — sections misusing H1 instead of H2/H3
Service pages and location pages have 8–10 H1 tags each. Every section subheading appears to be tagged as H1. Only one H1 per page is best practice.
▾

A well-structured page has exactly one H1 (the page's primary topic declaration) and uses H2/H3 for section headers and subheadings. Multiple H1s dilute the page's topical signal and make it harder for Google to understand the primary subject.

Fix

In HubSpot's page editor, open each affected page and review every text module. Any heading tagged as H1 that is not the primary page heading should be changed to H2 or H3. The rule: one H1 per page, positioned at the top, describing the page's primary topic. Section headers = H2. Subsections within a section = H3. This is a template-level fix — if pages share a module template where subheadings default to H1, fix the module and republish all instances.
